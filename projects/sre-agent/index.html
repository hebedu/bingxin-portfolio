从传统运维流程到可信、可控的 AI 运维协作

问题

传统运维排障信息分散、耗时，并依赖专家经验。

我的判断

运维需要的不是一个新的问答入口，而是能够跨系统取证、推进任务，同时保留人工控制的 Agent。

我的贡献

定义 Agent 能力边界，设计任务流、证据链、异常兜底与人工确认机制，并推动原型和研发交付。

02

问题定义

为什么传统排障效率低

用户为什么在排障中花了大量时间，却仍难以快速形成可靠判断。

CURRENT SITUATION / 传统排障

用户时间主要消耗在跨系统补齐上下文

收到异常告警后，用户需要在多个系统中分别查询指标、日志、链路、变更记录和历史案例，再对齐资源对象、环境与时间范围，逐步判断故障影响范围与可能根因。

  1. 01收到异常告警
  2. 02确认对象与影响范围
  3. 03查询指标与日志
  4. 04检查链路与变更
  5. 05比对历史案例
  6. 06推测可能根因
  7. 07决定处理方式

三类核心阻力

01

信息分散

指标、日志、链路、告警、变更记录和历史案例分散在多个系统，用户需要频繁切换页面和查询工具。

02

排查耗时

用户需要手动对齐资源对象、时间范围和异常现象，大量时间消耗在信息检索与比对。

03

依赖专家经验

故障范围与根因判断依赖对业务、服务拓扑和历史问题的经验，经验不足的用户难以快速建立完整排查路径。

核心问题不是缺少查询工具，而是用户必须在多个系统之间手动补齐上下文、建立证据关系并完成判断。

辅助论证 / Agent 趋势

AI 正在从回答问题转向执行任务

相比一次性问答，Agent 更强调围绕一个目标持续推进：理解任务意图，拆解执行步骤，调用工具获取信息，并根据中间结果继续判断下一步。

为什么用 Agent，以及它不该做什么

关键不是把聊天框放进运维平台，而是判断哪些任务适合 Agent 推进，哪些必须保留人工控制。

Agent 适配运维的三个原因

01

任务可以拆解

排障目标可以拆成告警确认、数据查询、证据比对、根因判断和处理建议。

02

需要多工具与多数据源

诊断过程天然依赖指标、日志、链路、变更记录、告警规则和历史案例。

03

结果可以验证

中间证据和最终判断都能被用户基于监控数据、历史案例和人工经验复核。

04

关键设计

如何让 Agent 可信、可控、可接管

这一章只保留三个关键设计决策，直接说明我如何把抽象的 AI 能力转成可交付的产品机制。

决策一

让用户进入正确的任务

问题
开放式聊天让用户难以理解 Agent 能做什么；模糊意图或缺失上下文可能导致系统进入错误工作流。
我的判断
先识别并找到用户的高频任务，再进入对应工作流。任务不明确时不应启动工具调用。
设计机制
  • 高频任务引导与展示
  • 意图识别是否正确
  • 用户审核任务理解并进行修改和调整
  • 信息不足时补齐资源对象、环境和时间范围
  • 意图不明确、信息缺失或信息错误时进入兜底，不启动工具调用
带来的价值
降低任务启动和试探成本，防止错误意图进入后续执行流程。
决策二

让结论可以验证

问题
用户无法确认 Agent 是否调用了真实数据，也难以理解结论如何形成；证据不足时，单一答案容易制造不可靠的确定感。
我的判断
诊断结果必须把数据来源、工具调用、事实、推断和建议分层展示，让用户能够基于证据验证或修正结论。
设计机制
  • 展示数据来源与工具调用状态
  • 区分事实、推断、根因假设与修复建议
  • 证据不足时降低确定性，说明缺失信息
  • 避免无依据输出，减少 AI 幻觉
带来的价值
让用户理解 Agent 为什么得出当前判断，并能够基于证据验证或修正结论，减少 AI 幻觉带来的误判风险。
决策三

让高风险操作可以接管

问题
运维操作可能直接影响生产环境。即使 Agent 能够生成修复方案，也不能忽略权限、影响范围和回滚风险。
我的判断
需要区分低风险分析与高风险执行后果：Agent 可以缩短分析路径，但关键执行权必须保留给用户。
设计机制
  • 查询、汇总和分析允许 Agent 自动推进
  • 修复方案和脚本由 Agent 生成，用户查看和修改
  • 脚本执行、配置变更和服务重启必须经过人工确认
  • 失败或中断时保留已有结果，支持重试、替代路径或人工接管
带来的价值
Agent 负责缩短分析路径，用户负责验证关键判断并决定是否执行。

待验证的业务指标

诊断任务完成率 平均故障定位时间 根因判断采纳率 修复建议采纳率 人工接管率 工具调用失败率

产品反思

第一阶段没有直接开放自动治愈，并不是 Agent 无法生成方案，而是执行权限、影响范围和回滚能力尚未达到可靠自动化的条件。对于高风险运维任务，自动化程度并非越高越好，关键是让用户理解依据、验证判断并保有最终控制权。

当前尚缺少长期真实用户行为数据，因此待验证指标仍需在实际业务中持续验证。现阶段产品验证更多来自内部业务需求与专家反馈；下一阶段需要进一步验证不同角色对证据深度、自动化程度和人工确认节点的差异化需求，并根据实际任务完成率、人工接管率和建议采纳率持续调整人机分工。

这个项目的关键不是把 AI 放进运维平台，而是把不透明的 AI 回答，转化为用户能够理解、验证和接管的任务协作过程。
